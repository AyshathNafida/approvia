# Admin invitations and college-email rollout (D16)

Approved 2026-10-24. **Migration, both Edge Functions and frontend deployed on 2026-10-24**, with disabled-email/access/privacy checks passed. Real email acceptance is pending. Live email and strict college-only access are disabled by default. Source: requirements sections 5–8, 20, 23–24 and decisions D6–D8/D16.

## Behavior

Admin invites Student/Faculty from Accounts after institutional record checks. Exact `lbscek.ac.in` addresses are normalized to lowercase; subdomains and lookalikes are refused. Students need an active class/department. Invitation names, account types and placement live in protected database records, not Auth metadata. Admin creation and account-type switching remain owner-controlled/out of scope.

Pending users have no application profile or request/configuration access. Auth creates/binds the invitation identity within its own transaction, before sending the invitation. Verified users set their password through the authenticated onboarding Edge Function; only after Auth succeeds does the service-only finalizer create their profile. Placement is rechecked. Passwords/tokens never enter application tables, logs or audit metadata. An independent `active` flag still controls onboarded accounts.

Accounts shows pending/sent/failed/completed invitations. Resend preserves original account details, checks a one-minute cooldown and a two-minute reservation lease, and uses a claim to ignore stale delivery results. Provider failure retains a retryable record; uncertain sends are not reported as success. An unrelated existing Auth identity is never adopted or deleted. Ask the owner to reconcile pre-existing unprofiled Auth identities; do not bypass onboarding with the retired provisioning RPC. Confirmed pending invitees receive a recovery link returning to guarded onboarding.

Only eligible active onboarded Faculty appear in assignment controls. Eligibility is checked again in assignment RPCs and request submission/decisions. Request RLS keeps D15 current/completed-step and scoped final-history rules; Admin still cannot read private requests.

Forgot password returns a generic response for college emails. Password setup/recovery is processed before workspaces render. Invalid/expired links show guidance; Admin can resend invitations and users can request another recovery link. `/auth/invite`, `/auth/recovery`, `/auth/email-change` are SPA routes; token-bearing URL fragments are removed after Auth consumes them.

## Interfaces and trusted boundaries

- `invite-account` accepts `{email, full_name, account_type, class_id}` for an authenticated active Admin. `account-access` accepts actions `settings`, `recover`, `onboard`, `migrate`. Redirects, migration identity, and onboarding identity are never taken from the caller's body.
- `account_access_status()` returns the caller's eligibility, feature flags, pending status and own approved migration target. `admin_eligible_faculty()` returns eligible Faculty IDs to Admin. Invitation listings use Admin-only column grants/RLS and exclude delivery claims.
- `admin_reserve_invitation` rechecks Admin/placement/domain and serializes with existing guarded writes. `account_delivery_result`, `account_onboarding_target`, `account_complete_onboarding`, `account_email_settings`, `account_migration_target` are executable only by the service role/owner. All old private helpers remain inaccessible to browser RPC callers.
- The eligibility source is current server-owned Auth email/verification plus protected active/onboarded profile fields. Stale JWT email claims and user metadata do not grant access. Existing serialized write behavior and D15 history are preserved.
- Onboarding password update and profile finalization span Auth/database calls. A finalization failure may leave a saved password but no application access; the UI explains retry/contact Admin. No distributed transaction or automatic identity deletion is claimed.
